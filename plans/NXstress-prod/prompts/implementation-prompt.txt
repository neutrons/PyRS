We are implementing a NeXus-compliant, NXstress-schema I/O feature for PyRS. The
backend is complete (`pyrs/utilities/NXstress/`); this work connects it to the
PyRS GUI. The plan is `plans/NXstress-prod/`.

This series has been through a **seven-axis audit**, and that changes how you
must read it. Do not begin implementing until you have done steps 0 through 2.


## The one thing most likely to mislead you

**Each subspec's body is NOT necessarily current.** Audit findings are recorded
in append-only `## Follow-up N` sections at the end of each document, and the
body is deliberately left as the record of what was believed. Where the two
disagree, **the Follow-up wins.**

**So read your subspec's Follow-ups first, and look specifically for items that
strike, supersede or re-scope something in the body above them.** They exist:
the first audit pass found that subspec 04's entire `## PyRS Changes` section
scheduled work that had already been done upstream -- removed by the very commit
the plan's claims were written against. An implementer reading only the body
would have done it twice. Assume yours may contain the same shape until you have
checked.

04's implementation pass then found the same shape twice more, so treat this as
the norm rather than a one-off: its instrument-name item named a workspace field
that does not exist anywhere in PyRS, and its rotation-order TODO turned out to
sit beside a larger defect than the TODO described. Both are in 04's Follow-up 7.

The single exception is a `path:LINE` citation, which is a pointer rather than a
belief: those were corrected in place, so the body's line numbers were accurate
as of LAST AUDIT PASS. They drift again as code moves, which is what
`landing_trigger.py` in step 2 exists to detect.

## While implementing

3. **Promote the probes and invariants this PR owns.** The principle is that **a
   finding which can be expressed as a test must be**, and the prose becomes a
   comment on the test: a paragraph is re-read once per audit, a test is checked
   on every commit. A probe is not itself a test -- it tests a design assumption
   before the code exists. Promoting means writing a real test that carries the
   same guarantee.

   **This list is deliberately not repeated here.** It lives in three places,
   each authoritative for a different thing, and copying it into this prompt
   would create a fourth copy that drifts -- the mechanism `process.md` section 9
   rejects. Read them:
   - the subspec's own `## Follow-up N` sections, under **"Invariants flagged,
     not written"** -- the invariant, its owner PR, and its tier;
   - `probes/README.md`'s **Disposition** column -- which probe each one comes
     from, and whether it is `promote` / `retire to record` / `stays a probe`;
   - `review/findings.md` section 5 -- the same set as one table, with an
     "Owner PR" and "Possible from" column, so you can see at a glance what this
     PR owns and what it merely unblocks.

   If those three disagree, that is itself a finding: record it rather than
   picking one.

   Two rules when you write them:
   - Place it by `CLAUDE.md`'s tier table. A test that constructs or drives a Qt
     widget is `tests/ui/` and needs **both** `@pytest.mark.gui` and
     `@pytest.mark.integration` -- `gui` alone drops it from the integration tier.
   - Where a probe reproduces a counterparty's logic **locally** rather than
     importing it (`a5_peakcollection_ranges.py` does), carry that property into
     the test. A test that imports the counterparty's own rule passes vacuously.

## Anti-patterns, from the audit that produced these documents

- **Re-reading a claim and finding it plausible is not verification.**
  Plausibility is what a stale claim has in abundance.
- **"The code that uses it does not exist yet" is not a reason to leave a
  third-party claim unprobed.** That reasoning was used once in this audit, and
  it was wrong -- the claims were about an installed package and existing source,
  executable all along.
- **A drifted line number does not imply a stale claim**, and an accurate one
  does not imply a true claim. Ten citations in the README's architecture tables
  were wrong while every sentence around them was correct.
- **"Accepted without raising" is not "harmless".** Report the resulting state,
  not just the absence of an exception -- an HDF5 name containing `/` raises
  nothing and silently creates a nested group.
- **Do not describe an array from its first few values.** The 04 pass printed
  `log[:5]`, saw five identical numbers, and wrote "this log is constant" into a
  Follow-up as evidence. Over all 150 values it varied by 60 mm; the five matched
  only because they were one row of a nested scan. A test caught it. The
  conclusion survived, the evidence did not -- print `min`/`max`/`ptp` and a
  count of distinct values before characterising real data.
- **A grep over the source is not a probe of the output.** Reading the order of
  the transformations `_instrument.py` writes told an earlier pass what was
  written; it could not show that seven of the eight were unreachable. Build the
  artifact and traverse it. (More of these in `probes/README.md`'s failure-modes
  table -- read it, per step 1.)
